## Paket A — P0: tutup bypass callback Linkqu (ISSUE-003)

**Bukti:** `Backend/src/api/webhook/webhook.service.ts`, `handleLinkQuCallback`:

- Signature hanya dicek di `if (signatureKey && incomingSignature)`. Menghilangkan signature melewati autentikasi, bahkan ketika key server tersedia.
- Nominal yang hilang atau `NaN` melewati pemeriksaan. Payload berisi referensi valid dan `status: 'SUCCESS'` tanpa signature/amount dapat masuk settlement.
- Status kosong dengan `response_code: '00'` dianggap pembayaran sukses. Provider/merchant lokal belum dicocokkan.
- Tes paralel di `linkqu-callback.spec.ts` justru memakai payload tanpa signature dan mengharapkan kredit.

**Instruksi:**

1. Tambahkan regression test yang menolak kredit untuk signature hilang, key kosong, signature salah, amount hilang/nonangka, status hilang/kontradiktif, dan identitas provider tidak cocok. Pastikan tidak ada mutasi saldo.
2. Baca kontrak resmi akun Linkqu untuk VA/QRIS/e-wallet. Simpan sumber dan fixture tersamarkan. Jangan mengesahkan HMAC `amount + partnerReff + status` hanya karena implementasi dan tes menghitung rumus yang sama.
3. Terapkan autentikasi yang didukung provider secara wajib sebelum settlement. Bila callback tidak menyediakan signature, verifikasi status server-ke-server yang didukung sebelum kredit. Konfigurasi/bukti yang tidak tersedia harus menghasilkan tidak ada kredit.
4. Validasi struktur, angka terbatas dan positif, referensi, provider/identitas merchant, serta nominal sesuai arti amount/fee yang dibuktikan kontrak. Jangan menerima salah satu dari amount/total secara sembarang.
5. Normalisasi status dengan tabel eksplisit. Field hilang/tidak dikenal/bertentangan tetap belum terverifikasi. Gunakan fixture kontrak untuk status/body HTTP acknowledgment melalui controller dan interceptor.

**Lulus bila:** payload valid yang terautentikasi memberi satu kredit; semua variasi invalid di atas memberi nol kredit. Tidak ada jalur alternatif yang melewati verifikasi.

## Paket B — P0: jangan buka ulang transaksi final (ISSUE-001)

**Bukti:** `Backend/src/administrator/transaksi_pulsa/transaksi_pulsa.service.ts::updateStatus` memanggil finalizer hanya untuk sukses/gagal; cabang lain menulis `proses` tanpa syarat. DTO mengizinkan `proses`. Finalizer hanya mengunci berdasarkan status, sehingga `gagal -> proses -> gagal` menghasilkan refund kedua.

**Reproduksi:** saldo awal 100.000, debit 10.000, finalisasi gagal mengembalikan menjadi 100.000. Panggil update admin ke proses, lalu finalisasi gagal lagi. Implementasi sekarang memungkinkan menjadi 110.000.

**Instruksi:**

1. Tulis regression test urutan tersebut, juga `sukses -> proses -> gagal`.
2. Larang perubahan dari status final kembali ke proses di DB update bersyarat. Hindari hanya pemeriksaan status di luar transaksi karena masih dapat balapan. Edit keterangan boleh melalui jalur terpisah tanpa mengubah status finansial.
3. Tambahkan identitas refund unik berdasarkan transaksi, dengan migrasi/backfill yang aman untuk data lama. Status saja tidak boleh menjadi satu-satunya bukti bahwa dana belum dikembalikan. Verifikasi transaksi memang pernah didebit sebelum refund data historis; jangan otomatis refund record tanpa bukti debit.
4. Pertahankan klaim, refund snapshot `selling_price + fee_agen`, dan ledger dalam transaksi yang sama. Bila member/relasi wajib hilang, jangan commit final gagal seolah refund berhasil.
5. Teruskan harga aktual tervalidasi dari callback dan cek admin ke finalizer. Saat ini `updateSuccessTransaction` mengabaikan field price/harga callback. Uji harga modal aktual berbeda dari snapshot. Dokumentasikan rumus laba dengan fee agen berdasarkan alur biaya yang benar; jangan menebak.
6. Hapus early return callback yang menyembunyikan konflik sukses/gagal sebelum finalizer; simpan konflik untuk rekonsiliasi tanpa debit/refund kedua.

**Lulus bila:** callback/detail/admin paralel dan urutan buka ulang di atas hanya menghasilkan satu refund/ledger. Uji dengan PostgreSQL nyata serta fault injection setelah klaim agar rollback terbukti.

## Paket C — P0: status settlement Linkqu tetap konsisten saat balapan (ISSUE-003)

**Bukti:** cabang gagal `handleLinkQuCallback` mengabaikan `count` dari klaim gateway `status: 'PENDING'`, lalu tetap mengubah RequestDeposit berdasarkan objek yang dibaca sebelum transaksi. Callback gagal yang membaca pending, menunggu callback sukses commit, kemudian melanjutkan dapat meninggalkan gateway SUCCESS, saldo terkredit, tetapi deposit gagal.

**Instruksi:**

1. Tulis tes PostgreSQL dengan barrier: kedua handler membaca pending; sukses commit dahulu; handler gagal lanjut. Assert kedua status tetap sukses dan kredit tepat sekali.
2. Perubahan RequestDeposit hanya boleh dilakukan oleh pemenang klaim transisi yang sah, dalam transaksi DB yang sama. Periksa count untuk jalur sukses maupun gagal; jangan mengandalkan `deposit.status` dari pembacaan luar.
3. Ganti klaim sukses `not: 'SUCCESS'` dengan daftar transisi yang disepakati. Sukses terlambat setelah expired/failed harus mengikuti kebijakan rekonsiliasi eksplisit, bukan menimpa semua status tanpa jejak.
4. Tambahkan constraint ledger settlement unik per deposit dan event unik. Pastikan relasi deposit/member valid sebelum menandai gateway sukses.
5. Referensi tidak ditemukan sekarang mendapat `response: '00'` tanpa event durable. Simpan inbox callback untuk retry, atau respons retry sesuai kontrak. Jangan membuang event yang datang lebih cepat dari penyimpanan lokal.
6. Buat laporan read-only kandidat gateway SUCCESS tanpa ledger/kredit untuk record lama. Jangan otomatis mengkredit kandidat.

**Lulus bila:** sukses/gagal paralel, dua deposit bersamaan debit, duplicate sepuluh kali, DB rollback, dan callback cepat menjaga status serta saldo konsisten.

## Paket D — P1: idempotensi pembelian persisten dan recovery (ISSUE-002)

**Bukti:** `transaksi.service.ts` menyimpan key dan SKU pada `[SNAPSHOT:...]` di `ket`, mencari key dengan `contains`, dan memakai `idempotencyInFlight` Map. Finalizer mengganti `ket` dengan SN/alasan sehingga replay setelah final dapat membuat pembelian/debit baru. Dua instance backend tidak berbagi Map. Request berbeda dengan key sama yang sedang berjalan langsung mendapat promise lama tanpa validasi payload. Failover menyimpan SKU baru di `failover.sku`, tetapi detail/admin membaca `snapshot.sku` lama. ID provider nonnumerik dimasukkan ke `serial_number`. Scheduler yang diperiksa hanya sinkronisasi produk; cek admin bukan recovery otomatis.

**Instruksi:**

1. Buat field/tabel intent dengan unique `(memberId, idempotencyKey)`, fingerprint payload tetap, referensi transaksi unik, serta snapshot provider/SKU/tujuan terpisah dari `ket`. Validasi panjang/format key tanpa pemotongan diam-diam. Replay harus tetap berlaku setelah final dan restart.
2. Simpan intent, debit dan pekerjaan submit dalam satu transaksi DB. Tangani konflik unique dengan membaca hasil intent lama dan mencocokkan fingerprint. Map boleh menjadi optimasi, bukan jaminan kebenaran.
3. Catat `saldo_sebelum` dari saldo hasil mutasi ditambah total debit; sekarang memakai `currentSaldo` sebelum transaksi sehingga audit saldo dapat salah saat dua debit berjalan.
4. Buat attempt persisten dengan referensi unik, provider, SKU, provider ID string, status dan waktu. Semua check dan callback harus cocok dengan attempt yang benar. Jangan taruh provider ID dalam SN. Audit seluruh pemanggil `trx_id` saat migrasi.
5. Gunakan fixture dari adapter/provider per provider untuk sukses/gagal/pending/unknown. Timeout bukan gagal final. Jangan biarkan kode respons yang belum dipahami otomatis refund.
6. Tambahkan worker durable untuk submit dan rekonsiliasi dengan lease/klaim, backoff, batas retry dan penanda manual review. Hubungkan ke modul/scheduler yang benar-benar dijalankan. Restart sesudah debit sebelum send harus ditemukan worker. Setelah hasil kirim ambigu, cek referensi lama; retry submit hanya jika kontrak menjamin aman.
7. Failover hanya setelah kegagalan definitif; attempt lama tetap tersimpan. Callback gagal attempt lama tidak boleh merefund pembelian yang sedang dijalankan attempt baru.
8. Mobile `konfirmasi_pembelian.dart` harus mempertahankan intent key melewati timeout dan restart, terikat akun/payload; sekarang key dibuat ulang di initState.

**Lulus bila:** dua instance backend dengan key sama menghasilkan satu debit/transaksi/pengiriman awal; replay sesudah sukses/gagal tetap transaksi lama; payload berbeda ditolak saat in-flight maupun selesai; restart pulih; perubahan mapping tidak mengganti SKU attempt; saldo sebelum/sesudah benar untuk dua pembelian bersamaan.

## Paket E — P1: idempotensi dan recovery create deposit (ISSUE-004)

**Bukti:** `deposit.service.ts::processLinkquDeposit` membersihkan lalu memotong key menjadi 25 karakter, tanpa membandingkan payload replay. Dua key berbeda dapat menjadi referensi sama. Timeout/metadata CREATED belum diproses worker. Create gagal mengubah gateway dan deposit melalui dua update terpisah tanpa klaim status. PIN boleh kosong dan email dibuat dari nomor telepon. `Promise.race(fetch)` hanya membatasi sampai header diterima, bukan pembacaan body.

**Instruksi:**

1. Gunakan intent unique member/key utuh atau hash deterministik, fingerprint nominal/metode/bank, dan referensi provider terpisah. Replay payload berbeda harus ditolak. Tangani unique conflict pada create paralel dengan replay hasil lama.
2. Pisahkan adapter Linkqu untuk endpoint, signature, environment, validasi kredensial/kontak, timeout hingga body selesai, normalisasi response/fee/expiry dan cek status. Gunakan AbortController/timeout yang mencakup seluruh request; abort tidak membuktikan provider belum menerima pembayaran.
3. Verifikasi kontrak field wajib, Permata/OVO, fee dan expiry dengan fixture resmi. Jangan mengirim identitas pelanggan rekaan. Tolak konfigurasi wajib yang kosong sebelum membuat pekerjaan eksternal. Validasi callback URL dari konfigurasi deployment.
4. Tambahkan pekerjaan durable create/reconcile bersama intent. Pulihkan crash sebelum send, timeout sesudah provider menerima, dan DB error sesudah respons sukses tanpa membuat invoice kedua.
5. Jalur kegagalan create harus atomik untuk gateway/deposit dan bersyarat agar tidak menimpa settlement yang sudah sukses. Respons ambigu tidak otomatis gagal final. Fee harus finite, valid dan sesuai kontrak sebelum penjumlahan.
6. Hindari endpoint detail yang menebak satu angka sebagai gateway ID atau RequestDeposit ID sekaligus; gunakan UUID/jenis ID yang eksplisit untuk mencegah memilih invoice lain milik member yang sama. Pertahankan filter pemilik dari JWT/relasi.

**Lulus bila:** parallel create/retry/restart satu intent menghasilkan satu invoice; key dengan prefiks 25 karakter sama tetap berbeda; key sama payload berbeda ditolak; kegagalan create yang balapan dengan settlement tidak menimpa sukses; seluruh instruksi bisa dibaca ulang tanpa create baru.

## Paket F — P1: outbox notifikasi dan pemulihan Mobile (ISSUE-001/003/005)

**Bukti:** finalizer dan settlement memanggil FCM sesudah commit tanpa outbox. Crash pada sela commit/send menghilangkan notifikasi selamanya karena replay status final tidak mengirim ulang. `sendPengumuman` menulis Success jika satu penerima berhasil meski penerima lain gagal. `pengumuman_provider.dart` masih mencetak token FCM penuh; update token menelan error; listener tidak dibatalkan; cold start ditandai handled sebelum navigasi siap; foreground hanya refresh pengumuman.

**Instruksi:**

1. Simpan event bisnis unik di transaksi DB finalisasi/settlement. Worker menyimpan hasil per penerima, FCM message ID dan retry sementara; token invalid tetap dibersihkan. Dedup dengan event ID stabil. Gunakan outbox yang sama untuk paket lain jika sesuai, bukan beberapa implementasi paralel.
2. Agregasi hasil partial/failed/skipped secara jujur dan perbarui konsumen admin. `Sent` berarti diterima FCM, bukan diterima perangkat; jangan isi delivered_at seolah delivery perangkat sudah terbukti.
3. Pisahkan pemasangan listener dari sinkronisasi token yang dapat diulang saat login/koneksi pulih. Simpan/cancel subscription dan cegah init paralel memasang listener ganda.
4. Periksa response HTTP token dan jadwalkan retry terbatas. Audit login/logout/pergantian akun dan binding device; pending notifikasi/navigasi harus terkait akun yang tepat.
5. Simpan navigasi cold start sampai auth/navigator siap. Tandai handled setelah navigasi diterima, bukan sebelumnya. Foreground transaksi/deposit harus refresh saldo/detail/riwayat terkait dan memberi indikator terlihat.
6. Hapus log token penuh serta response yang memuat token/device pribadi. `updateFcmToken` tidak perlu mengembalikan objek device lengkap ke Mobile.

**Lulus bila:** worker mati sesudah commit dapat pulih; hanya penerima sementara gagal yang di-retry; token sync gagal kemudian pulih; logout A/login B tidak membuka detail A; foreground/background/terminated diuji. Catat uji perangkat nyata terpisah dari mock.

## Paket G — P1: webhook dan pengiriman WAPI Sender (ISSUE-006)

**Bukti:** route `webhookWapisender` langsung memproses body tanpa autentikasi. `WapisenderService.sendMessage` menerima JSON apa pun sebagai sukses kecuali `status` tepat false/string false; `{}` juga menjadi sent. Handler mengabaikan hasil `success:false` karena hanya menangkap exception. Dedup event memakai findFirst log sukses tanpa constraint unik. Balasan langsung setelah commit bisa hilang saat restart. Member.kode belum unique; lookup sebelum create tidak mencegah tabrakan paralel. Log menyimpan nomor dan kode verifikasi lengkap.

**Instruksi:**

1. Baca `wapisender_docs.pdf` dan kontrak akun yang berlaku; buat fixture autentikasi/event/send/ack resmi. Jangan mengarang header atau status sukses. Autentikasi harus diverifikasi sebelum registrasi/balasan.
2. Parser harus mengenali sukses eksplisit; JSON kosong/status tak dikenal/penolakan HTTP 200 bukan sukses. Timeout harus mencakup body. Handler wajib menangani hasil terstruktur, bukan hanya exception.
3. Normalisasi nomor secara konsisten saat registrasi, lookup dan penyimpanan; migrasi nomor lama dengan laporan tabrakan sebelum menambah/mengubah constraint. Tambahkan member code unik dengan retry konflik DB, bukan hanya findFirst sebelum create.
4. Simpan inbox event unik dan outbox balasan dalam transaksi registrasi. Pertahankan klaim temp_registrasi. Retry balasan tidak boleh mengulang registrasi. Event invalid yang diulang juga tidak boleh membanjiri pesan.
5. Worker retry sesuai kategori; hasil kirim ambigu jangan diulang membabi buta tanpa dukungan idempotensi/status provider. Redaksi nomor/kode/token pada log dan payload tersimpan yang tidak diperlukan.

**Lulus bila:** event paralel satu member/satu pekerjaan balasan; DB rollback nol pesan sukses; crash sesudah commit pulih; `{}`/penolakan HTTP 200 bukan sent; payload tanpa autentikasi tidak mendaftarkan akun. Smoke test hanya nomor uji tim.

## Paket H — P1: selesaikan alur Mobile deposit (ISSUE-007)

**Bukti:** `services/deposit.dart::processLinkquDeposit` hanya mengirim nominal/metode/bank, sehingga key backend belum digunakan. `PaymentInstructionScreen` membuat timer delapan detik tanpa batas/lifecycle observer, tidak mengunci request otomatis, tidak refresh saldo/riwayat saat sukses. QR fallback hanya SelectableText dan tombol salin, belum QR yang bisa dipindai. `.toLocal()` diberi label WIB meski zona perangkat berbeda. `_launchUrl` belum menangani URI invalid/exception.

**Instruksi:**

1. Setelah kontrak paket E siap, teruskan key persisten dari PaymentMethodScreen melalui DepositProvider dan service. Satu intent/account/payload memakai key sama sampai hasil diketahui. Tambahkan guard double tap serta try/finally agar loading pulih saat error.
2. Ambil detail saat layar dibuka/resume. Batasi polling, satu request aktif, hentikan saat background/route tidak aktif/dispose/final; resume boleh refresh. Jangan create hanya untuk refresh.
3. Pada sukses backend, refresh Beranda/saldo dan riwayat melalui provider yang sudah ada. FCM/socket memakai jalur refresh yang sama; tetap berfungsi tanpa FCM.
4. Render QR lokal dari qris_text memakai library yang sesuai dependensi proyek. Image gagal harus fallback ke QR text, bukan hanya teks panjang. E-wallet push-only memakai instruksi terverifikasi; kembali dari wallet tetap pending sampai server sukses.
5. Perbaiki zona waktu: konversi eksplisit ke WIB atau tampilkan zona lokal dengan label benar. Validasi URL/scheme dan tangani kegagalan launch tanpa crash.
6. Buat widget test dengan fake clock, repository pembayaran yang bisa di-inject, HTTP/provider mock dan Google Fonts tanpa unduhan. Dispose widget/timer di akhir. Hindari tanggal kedaluwarsa tetap yang membuat tes berubah hasil mengikuti waktu.

**Lulus bila:** create -> callback terverifikasi -> satu kredit -> instruksi/detail/saldo konsisten; restart pending membuka invoice sama; QR text dapat dipindai; offline lalu resume pulih; polling tidak tumpang tindih; member B ditolak mengambil pembayaran A. Tes widget tampilan saja tidak cukup.
